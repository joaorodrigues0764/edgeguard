# Controlled Cloudflare staging validation

The [initial hosted REST evaluation](analysis-evaluation.md#follow-up-and-milestone-closeout) is complete. The staging Worker has yet to be deployed and its D1 database and queues have yet to be provisioned. The next proposed stage is an isolated Worker integration trial with a **$0 spending ceiling and zero AI calls**. Provisioning, remote migrations, deployment and synthetic traffic each require explicit approval.

## Account and cost check before authorisation

- Record the operator, account ID, active Workers plan, billing mode, UTC time and remaining allowances. Match the account in the dashboard to `wrangler whoami` and `CLOUDFLARE_ACCOUNT_ID`. Verify permission to invoke Workers AI. For later provisioning, separately verify access to manage Workers, secrets, D1, Queues, Analytics Engine and AI Gateway in that account. Keep the deployment credential out of the evaluation process. [Workers AI token permissions](https://developers.cloudflare.com/workers-ai/get-started/rest-api/)
- Read today's actual Neuron usage in the Workers AI dashboard. Under Standard billing, the daily allocation is 10,000 Neurons, shared across the account and reset at 00:00 UTC. Workers Paid can incur USD 0.011 per additional 1,000 Neurons. Confirm model availability and rate limits. [Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/) · [AI limits](https://developers.cloudflare.com/workers-ai/platform/limits/)
- Inspect **edgeguard-staging** in AI Gateway. Record Standard or Unified billing, available credits, auto-recharge, logging, guardrails, retries and routing. For a zero-spend trial, require confirmed Standard billing, sufficient allowance, one upstream attempt, and no chargeable add-ons or fallback routes. Creating a gateway, buying credits or changing billing settings needs separate approval. [Gateway settings](https://developers.cloudflare.com/ai-gateway/configuration/manage-gateway/) · [Gateway pricing](https://developers.cloudflare.com/ai-gateway/reference/pricing/)
- Record the approved case, model, maximum calls and money limit. At the published model rates, 1,000 input tokens and 550 output tokens would represent about 139 Neurons or USD 0.00153 before allowances. The input count is illustrative. The output cap is 550. Reconcile actual usage with the account dashboard and billing records. [Model pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)
- For an integration test, also check Workers requests and CPU, D1 database count, storage and rows read/written, queue count, operations and retention. Free-plan reference points include 100,000 Worker requests/day, 500 MB per D1 database and 24-hour queue retention. Redelivery adds queue operations. Include Workers Logs and Analytics reads/writes in the inventory. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) · [Queues limits](https://developers.cloudflare.com/queues/platform/limits/) · [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) · [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/) · [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) · [Analytics Engine pricing](https://developers.cloudflare.com/analytics/analytics-engine/pricing/)

## Any future REST evaluation

1. Obtain approval to create `edgeguard-staging` and a dedicated, account-scoped Workers AI token if needed. Verify gateway ownership, settings and quota immediately before the run. Keep the token in a secret manager or protected shell environment.
2. Obtain approval for exactly **one** synthetic REST attempt, including the agreed spending ceiling. Set `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` and `AI_GATEWAY_ID=edgeguard-staging`. From the repository root, the authorised command would be `npm run --silent eval:analysis:live -- --live successful-opener`. Use the [evaluation guide](analysis-evaluation.md) to capture a private review artifact if needed.
3. Stop after that attempt, including on timeout, HTTP error, invalid output or unavailable usage. Stop before starting if identity, limits, billing, gateway settings or the budget cannot be verified. Compare the JSONL row against the gateway request count, Neuron usage and billing mode. A timeout can still consume quota. A second invocation, `all` (currently seven attempts), an admin retry, the live demo and any queue-triggered analysis require a new budget and approval.

## Isolated Worker setup

| Target                                 | Staging value                                                                                                            |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Worker                                 | `edgeguard-staging` on its own workers.dev URL, preview URLs disabled                                                    |
| D1                                     | `edgeguard-staging-db`, new UUID, shared repository migrations                                                           |
| Queue producer and consumer            | `edgeguard-staging-events`                                                                                               |
| Dead-letter queue                      | `edgeguard-staging-events-dlq`                                                                                           |
| Analytics Engine writer and SQL reader | `edgeguard_staging_telemetry`                                                                                            |
| AI binding and gateway                 | `AI` and `edgeguard-staging`                                                                                             |
| Rate limiting                          | Operator selects an unused positive integer namespace in the verified account                                            |
| Secrets                                | Fresh `INGEST_API_TOKEN`, `DASHBOARD_API_TOKEN`, `ADMIN_API_TOKEN` and `DASHBOARD_PASSWORD` scoped to the staging Worker |

Staging has no Cron Trigger, so scheduled recovery generates no background traffic. The queue consumer can still call AI when an incident opens. Use only synthetic inputs and keep external producers disconnected. The SQL binding derives its scope from the Worker account. The application checks the staging dataset before dispatch, allows only two literal dataset names in SQL, and binds the time range as values. The writer's target is set by Wrangler. Its first write creates the dataset. Wrangler 4.145.0+ supports the separate `analytics.binding` setting, and the lockfile pins 4.147.0. Rate limiters with the same account and namespace share counters. [Analytics SQL binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/analytics-sql/) · [Dataset syntax](https://developers.cloudflare.com/analytics/sql-api/datasets/) · [Analytics Engine bindings](https://developers.cloudflare.com/analytics/analytics-engine/get-started/) · [Rate limiting namespaces](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)

1. **Prepare locally.** From the root run `node staging/check.mjs --init`. This creates an ignored `staging/wrangler.local.json` with three explicit placeholders and a pre-deployment check. It refuses to overwrite an existing file. CI and local Vitest use synthetic bindings. The checked-in staging template blocks deployment.
2. **Provision only after approval.** In the verified account, check the resource inventory for existing names and owners. Obtain approval to create the named D1 database and two queues, reserve the namespace, and create any missing gateway. Record returned IDs and ownership. Fill in only `account_id`, `database_id` and `namespace_id` in the local file. Never import production data or secrets. Wrangler can provision omitted IDs during deployment. [Wrangler provisioning](https://developers.cloudflare.com/workers/wrangler/configuration/#automatic-provisioning)
3. **Verify offline.** Run `node staging/check.mjs` from the root. It rejects missing IDs, the configured production D1 UUID or namespace, and differences from the reviewed bindings and routes. A pass confirms configuration shape and isolation against the repository. Only the operator's account inventory can establish that a UUID belongs to the named staging database and the namespace is unused. Confirm the D1 name/UUID and both empty queues before running any remote command.
4. **Migrate after separate approval.** From the repository root use `cd staging`. For all commands below, remain there and use the locked Wrangler binary with the explicit local configuration. On a new, empty staging DB, review the repository SQL, list pending migrations, apply them and list again. A partial failure calls for inspection of the migration table before any retry. [D1 migration commands](https://developers.cloudflare.com/d1/wrangler-commands/)

   ```sh
   ../node_modules/.bin/wrangler d1 migrations list edgeguard-staging-db --remote --config wrangler.local.json
   ../node_modules/.bin/wrangler d1 migrations apply edgeguard-staging-db --remote --config wrangler.local.json
   ../node_modules/.bin/wrangler d1 migrations list edgeguard-staging-db --remote --config wrangler.local.json
   ```

5. **Deploy only after approval of the Worker, consumer and new secrets.** Generate four distinct staging secrets in a password manager. Use at least 32 characters for the dashboard password. Supply the four entries in a protected JSON or dotenv file outside the checkout. Recheck account identity and bindings, then use `../node_modules/.bin/wrangler deploy --config wrangler.local.json --secrets-file "$STAGING_SECRETS_FILE"` from `staging/`. The root deployment script targets production. [Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/)
6. **Verify with an approved synthetic request budget.** Confirm the Worker URL, active version, bindings, queue consumer and empty backlog in the dashboard. Check `GET /health`, then a protected metrics request without a token (expect 401). With the staging ingest token, send one healthy event on a new synthetic route. With the staging read token, confirm D1 persistence and query `/api/metrics/telemetry?hours=1` after the first write becomes visible. Verify the staging dataset and gateway count. A fresh, healthy route should produce zero inferences. Stop on unexpected traffic, a 503, a resource mismatch, pending deliveries or extra gateway calls.

## Rollback and cleanup

Stop sending events. If the consumer might issue more AI calls, pause its deliveries in the dashboard and revoke staging ingest access. Inspect staging queue depth, DLQ, AI usage and billing. Obtain approval before rollback or deletion and record exactly which names and IDs are affected. Roll back only the staging Worker to a compatible previous staging version if one exists. A Worker rollback leaves migrations and queued data in place. [Worker rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/) · [Queue delivery controls](https://developers.cloudflare.com/queues/configuration/pause-purge/)

For a disposable first deployment, remove the staging consumer/Worker, then the two confirmed staging queues and dedicated D1 database after approval to discard their synthetic contents. Remove the dedicated gateway if unused, revoke its evaluation credential, destroy staging secrets and retire the namespace from the account inventory. Removing the writer stops new data points. Analytics Engine retains written data for three months. Check remaining resources, gateway credits, pending charges and usage after cleanup. [Analytics Engine retention](https://developers.cloudflare.com/analytics/analytics-engine/limits/)
